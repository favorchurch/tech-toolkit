# Favor Tech Scalable System Toolkit

**Open-source playbooks for launching and sustaining excellent Tech ministry across campuses.**

> Status: **Version 0.1 — field-validation draft** (28 October 2026). This is an operational starter kit, not a declaration that any campus has been certified. Functional leads must validate locally variable details before use in live services.

## Start here

1. Read the [orientation and document map](docs/START-HERE.md).
2. Understand our [vision, organization, and roles](docs/CHARTER.md).
3. Pick your team:
   - [Internet & streaming](playbooks/internet/README.md) — onsite connectivity, streams, volunteers, incident recovery.
   - [Website](playbooks/website/README.md) — requests, content, design, quality assurance, publishing.
   - [App Development](playbooks/app-development/README.md) — products, Rock-connected systems, engineering, deployment, support.
4. Launch a campus using the [three-stage campus launch guide](launch/README.md).
5. Use the [training program](training/README.md), [forms and checklists](templates/README.md), and [coverage crosswalk](docs/COVERAGE.md).

## The four decisions that shape this toolkit

| Decision | Standard |
| --- | --- |
| Campus operating model | **Centrally governed, locally operated.** Campuses run routine ministry work; Central Tech governs common platforms, architecture, security, and privileged releases. |
| Publication and security | **Open-source, sanitized playbooks.** Public documents describe portable processes. Actual sensitive campus configurations are restricted; credentials stay in a vault. |
| Campus certification | **Prepare → Assisted Launch → Certified.** Service count is not a substitute for competency and recovery evidence. |
| Documentation ownership | **Distributed ownership, centralized standards.** Functional leads maintain their playbooks; campus leads maintain local addenda; Central Tech approves global standards. |

## Operational principle

A new campus should be able to execute an ordinary service, publish approved content, and seek software support without dependence on undocumented Manila knowledge. An operator must also know **when to stop and escalate** instead of changing shared systems.

## What is and is not included

- **Included:** responsibilities, SOPs, process flows, checklists, templates, learning paths, equipment categories, quality standards, readiness gates, and escalation patterns.
- **Excluded:** live passwords, cloud credentials, administrative endpoints, access tokens, active security rules, detailed internal topology, private personnel records, and real campus-specific emergency contacts.
- **Linked, not copied:** specialist repository READMEs, especially the existing [Internet Playbook](https://github.com/favorchurch/internet-playbook). Local venue procedures live in restricted campus addenda, not this public repository.

## Version and validation

This is a first published framework, not a completed security audit or a campus launch authorization. The [roadmap and evidence gaps](docs/ROADMAP.md) identify the outstanding lead interviews, historical-document review, and pilot rehearsals. Do not treat examples as live service settings.
