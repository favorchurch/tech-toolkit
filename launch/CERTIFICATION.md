# Evidence-based readiness and campus certification

## Principle

**Mandatory critical controls cannot be traded for an aggregate score.** Pass/fail is based on demonstrated ability and verified operational evidence. A checklist alone is not a certificate.

## Gate A — Prepare

| Domain | Demonstration | Critical? |
| --- | --- | --- |
| Leadership | Named campus owner, shift Captain and Central Tech escalation path | Yes |
| Physical safety | Approved power and cable safety | Yes |
| Access/data | Least-privilege model and private-record custody verified | Yes |
| Connectivity | End-to-end test of each declared essential live workflow | Yes |
| Continuity | Documented degraded mode or explicitly approved no-go choice | Yes |
| Streaming | Destination/viewer check when streaming is a critical ministry function | Conditional: yes if critical |
| Website | Authorized owner and review/publishing route | Yes |
| App support | Known escalation path and ability to provide redacted reproduction | Yes |
| Inventory | Required assets and spares available and tracked | Yes |
| Training | Primary/backup role competency and assessed handover | Yes |

A conditional critical test becomes mandatory whenever the related ministry service is in scope.

## Gate B — Assisted Launch evidence

For each event/session, log:
- Event and campus label (without people/attendee records);
- Operated critical workflows and local people/roles assigned privately;
- Preflight pass/fail with independent viewer/user verification;
- Any Central Tech intervention (reason, extent, ownership);
- Degraded modes used, time and outcome;
- Local operator's response and safe escalation;
- Packdown, incidents and corrective action owners.

An Assisted Launch can include safe, documented limitations; it cannot hide failing safety or security controls.

## Gate C — Certified Independent Operations

The local team must independently demonstrate:

1. Preflight and declared service readiness.
2. Normal live operation and a clean handover.
3. A deliberately controlled, non-destructive connectivity or streaming failure rehearsal with restoration proof.
4. A low-risk website content request review and QA path without unauthorized privileged access.
5. A cross-campus app problem report with clear evidence, authorized escalation and correct data-handling boundaries.
6. Equipment custody and post-service closure.
7. A current private campus addendum and approved permissions.

Central Tech and relevant functional leads jointly review scope-specific evidence before marking **Certified**.

## Decision recording

| Status | Meaning |
| --- | --- |
| **Prepared** | Gate A passed, not yet independently proven |
| **Assisted** | Operating with formally agreed Central Tech support |
| **Certified — scoped** | Evidence demonstrates competence in named functions |
| **Conditional** | Minor noncritical constraints accepted by named authority; not a substitute for mandatory gates |
| **Suspended / Reassess** | Material changes or incident invalidate prior evidence |
| **Not ready** | At least one mandatory gate failed |

## Reassessment triggers

New venue, major network/stream platform replacement, permission model change, new sensitive app use, responsible lead turnover, material incident or prolonged training gap. Functional lead records which tests must be repeated; full retest is not automatically required for an unrelated change.

## Evidence privacy

Store witnesses, exact contacts, real diagrams, privileged records and system logs in restricted evidence storage. Public repositories contain only blank templates and policy.
